## Problem Statement（問題陳述）

團隊要参加「2026 雲湧智生：臺灣生成式 AI 應用黑客松競賽」，中華電信命題為「城市交通應變 AI 指揮台」。需要在 7 天內從零開始，建立一個能協助交通指揮官在 60 秒內做出可靠決策的 AI 交通指揮系統，並提交提案簡報、可運作的 Dashboard 和完整原始碼。

---

## Solution（解決方案）

建立一套 Dashboard 決策中樞，具備「自動感知」與「互動決策」兩種能力：

1. **自動感知**：系統沿時間軸自動讀取官方車流與電信信令資料，依 SOP 7 條規則判定事件級別
2. **互動決策**：突發事件注入後，60 秒內完成路網重規劃，產出交控中心建議書與多語化民眾簡訊
3. **What-if 模擬**：指揮官可輸入假設情境，系統重新套用 SOP 模擬結果

### 核心技術分工

| 元件           | 負責內容                                         |
| -------------- | ------------------------------------------------ |
| 決定性程式碼   | 資料解析、分級判定、SOP 觸發、路徑篩選、ETE 計算 |
| Amazon Bedrock | 建議書措辭、民眾警示、決策解釋、What-if 互動     |

## User Stories（使用者故事）

### 模組 1：動態時序監測儀表板

1. 作為交控中心指揮官，我想要儀表板依時間軸自動呈現車流與人流狀態，以便掌握全市即時交通狀況
2. 作為交控中心指揮官，我想要當數據達到 SOP 預警門檻時自動跳出預警提示，以便無需人工查詢即可掌握異常
3. 作為交控中心指揮官，我想要以紅燈標示 A 級路段、黃燈標示 B 級路段，以便快速識別嚴重程度
4. 作為交控中心指揮官，我想要看到 15 條核心路段的即時飽和度，以便判斷整體交通狀況

### 模組 2：突發事件注入與處置

5. 作為系統管理員，我想要將 live_incidents.json 事件注入系統，以便啟動應變流程
6. 作為交控中心指揮官，我想要系統在 60 秒內完成路網重規劃並更新畫面，以便快速回應突發災情
7. 作為交控中心指揮官，我想要系統依 SOP 第 2 條自動找出主要與次要疏散路線，以便提供改道指引
8. 作為交控中心指揮官，我想要系統排除不適合的道路並說明排除理由，以便決策有據可查
9. 作為交控中心指揮官，我想要系統計算預計恢復時間 (ETE)，以便掌握恢復時程

### 模組 3：對話式策略諮詢顧問

10. 作為指揮官，我想要在對話視窗輸入假設性問題（What-if），以便驗證 SOP 邏輯與預期動作
11. 作為指揮官，我想要系統先顯示精簡策略摘要，再提供應觸發的 SOP 條款、預期動作與詳細解釋，以便快速評估假設情境
12. 作為指揮官，我想要系統在回答中引用對應的 SOP 條款，以便確認判斷依據

### 模組 4：AI 決策推理與解釋鏈

13. 作為評審與指揮官，我想要在儀表板看到 AI 之推理過程，以便理解判定與排除之理由
14. 作為評審與指揮官，我想要系統引用作為判定依據之 SOP 條款，以便確認合規性
15. 作為評審與指揮官，我想要系統解釋為何排除特定替代道路，以便理解決策邏輯

### 模組 5：數位通報與多語化

16. 作為交控中心指揮官，我想要系統於漫遊比率偏高時自動產出多語告警，以便通報含外籍人士之群眾
17. 作為交控中心指揮官，我想要系統提供一鍵發布功能，以便快速對外通報
18. 作為外國旅客，我想要收到英文（或日文、韓文）的警示訊息，以便了解改道資訊

### SOP 規則邏輯

19. 作為系統，我需要依 SOP 第 1 條判定交通擁塞級別（B 級 0.85~0.95，A 級 >= 0.95），以便決定紅黃燈顯示
20. 作為系統，我需要在城市應變觸發路段（RD_TPE_001、RD_TPE_002）達 B 級時啟動長綠燈時制，以便疏導交通
21. 作為系統，我需要依 SOP 第 2 條三要件觸發車禍與路障應變，以便啟動疏散流程
22. 作為系統，我需要從 alternatives 中篩選容量 >= 1000、直接相交、上游位置的候選路段，以便選出主疏散路徑
23. 作為系統，我需要依 SOP 第 3 條偵測捷運人流（Growth > 0.30 或 Count > 25000），以便啟動接駁分流
24. 作為系統，我需要依 SOP 第 4 條偵測大巨蛋散場（歷史峰值 >= 30000 且 Growth <= -0.20），以便提前連動接駁
25. 作為系統，我需要依 SOP 第 5 條處理號誌故障（type = Power_Failure 或描述含故障），以便產出人工指揮建議
26. 作為系統，我需要依 SOP 第 6 條觸發多語化通報（任一基地台 Roaming >= 30%），以便通報外籍人士
27. 作為系統，我需要依 SOP 第 7 條計算 ETE（base_clearance + congestion_penalty），以便提供恢復時間預估

### 交付物

28. 作為參賽團隊，我需要提交提案簡報（含 AWS 架構圖），以便符合評審要求
29. 作為參賽團隊，我需要提供可運作的 Dashboard 部署網址，以便評審體驗
30. 作為參賽團隊，我需要錄製展示影片，以便評審觀看
31. 作為參賽團隊，我需要提供 GitHub 完整原始碼，以便評審審查

### 加分項目

32. 作為參賽團隊，我需要 Dashboard 外觀設計具直觀性與設計性，以便取得加分
33. 作為參賽團隊，我需要多語化通報支援日文、韓文，以便取得加分

## Implementation Decisions（實作決策）

### 1. 技術選型

| 決策      | 選擇                 | 理由                            |
| --------- | -------------------- | ------------------------------- |
| 主要語言  | TypeScript           | 隊伍多數人熟悉，與 React 同語言 |
| 前端框架  | React/TS SPA         | 官方建議，隊伍有 React 人才     |
| 雲端平台  | AWS                  | 官方指定                        |
| 生成式 AI | Amazon Bedrock       | AWS 原生，唯一合規選擇          |
| 基礎設施  | AWS CDK (TypeScript) | 與主要語言同，利於參數化        |
| 開發環境  | LOCAL_MOCK 先行      | 7 天內先確保能跑，再上雲端      |

### 2. 系統架構

| 決策     | 選擇                    | 理由                       |
| -------- | ----------------------- | -------------------------- |
| 決策分離 | 決定性程式碼 > AI       | 可靠、可稽核、符合評審要求 |
| AI 角色  | 文字生成 + What-if 理解 | 平衡策略，不冒險           |
| 編排方式 | Lambda 直接編排         | 7 天內先用最簡單方案       |
| 前端託管 | Amplify Hosting         | 最快上線                   |

### 3. 資料處理

| 決策           | 選擇                                  | 理由                           |
| -------------- | ------------------------------------- | ------------------------------ |
| 時間對齊       | 取最近 prior（Strategy A）            | 不用未來資料，符合即時監控邏輯 |
| affected_road  | 忽略不使用（Strategy B）              | SOP 第 3 條未提及此欄位        |
| ETE 受影響路段 | 事故路段 + alternatives（Strategy C） | 最小合理範圍                   |
| 事故錨點解析   | LLM 解析 + 程式確認（Strategy D）     | 平衡準確性與彈性               |
| 多語範圍       | 全資料集基地台（Strategy F）          | 最嚴格解釋，不漏警報           |

### 4. Demo 範圍

| 決策     | 選擇                   | 理由           |
| -------- | ---------------------- | -------------- |
| 事件數量 | 3 個全做               | 隊伍選擇豪華版 |
| What-if  | 做                     | 官方要求       |
| 多語     | 中英 + 日韓加分        | 評審加分項目   |
| 報告     | 15 頁簡報 + 3 分鐘影片 | 黑客松標準     |

## Testing Decisions（測試決策）

### 測試原則

1. **只測外部行為，不測實作細節** — 測試應驗證「系統做什麼」而非「系統怎麼做」
2. **屬性導向測試 (PBT)** — 使用 fast-check 進行隨機測試，確保規則在各種輸入下正確
3. **邊界測試** — 每個 SOP 門檻值都要測試邊界（如 0.8499 vs 0.85）
4. **黃金測試** — 使用 3 個官方事件作為黃金測試案例

### 測試模組

| 模組     | 測試類型       | 重點                     |
| -------- | -------------- | ------------------------ |
| 資料解析 | 單元測試       | 5 個官方檔案的解析正確性 |
| 規則引擎 | PBT + 邊界測試 | 7 條 SOP 的觸發條件      |
| ETE 計算 | 單元測試       | 公式計算正確性           |
| API      | 整合測試       | 請求/回應格式            |
| 前端     | 視覺測試       | 畫面顯示正確             |

### 測試案例

- TC-SAT-001~004: Saturation Score 邊界
- TC-SOP3-001~004: SOP-3 觸發邊界
- TC-SOP6-001~002: SOP-6 觸發邊界
- TC-SOP2-001~002: SOP-2 容量邊界
- ACC_001 Golden: 光復南路車禍完整場景
- EVT_002 Golden: 捷運人流完整場景
- EVT_003 Golden: 號誌故障完整場景

## Out of Scope（超出範圍）

1. **不使用外部網路搜尋資料** — 只用官方提供的 5 個資料檔案
2. **不建立產品程式碼** — 本次只做黑客松 demo，不做正式產品
3. **不處理多事件同時發生** — 一次只處理一個事件
4. **不建立真實的跨系統整合** — 北捷、公車處、警力以文字請求呈現，不真的 API 串接
5. **不優化效能** — 7 天內先求功能正確，效能之後再說

## 測試 Seam（接縫）

本專案的測試接縫建議如下：

```
┌─────────────────────────────────────────────────────────┐
│                     前端 (React)                         │
│  Seam 1: API 回應 → 畫面渲染                              │
└─────────────────────┬───────────────────────────────────┘
                      │ HTTP/WebSocket
┌─────────────────────▼───────────────────────────────────┐
│                   後端 (Lambda)                          │
│  Seam 2: 請求 → 決策核心 → 回應                          │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│               規則引擎 (Domain)                          │
│  Seam 3: 事件 + 資料 → SOP 判斷 → 決策結果               │
└─────────────────────┬───────────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────────┐
│               資料解析 (Ingestion)                        │
│  Seam 4: 原始檔案 → 型別化記錄                            │
└─────────────────────────────────────────────────────────┘
```

**建議主要測試接縫**: Seam 3（規則引擎）— 這是整個系統的核心，所有其他模組都依賴它的輸出。
